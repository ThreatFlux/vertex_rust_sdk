# glibc code-scanning alert review

This records the original glibc-based artifacts. See the [subsequent remediation](remediation.md) for the static runtime fix and current alert dispositions.

Reviewed 2026-10-21. Scope: the 14 open `libc6` alerts with CVE years 2020 onward in the GitHub export supplied for this review. Historical glibc findings are reviewed separately. No alerts were dismissed.

## Evidence and classification limits

The exported alerts identify `libc6 2.41-12+deb13u4` in scan category `.github/workflows/docker.yml:scan`, commit `3b990a75b9cef5fc43dffa45ad8851078177998f`. The Dockerfile at that commit pins `gcr.io/distroless/cc-debian13:nonroot@sha256:e792ab3d241a468a4fd7519ddbbebe66b49b5f365771716ea688ad40b6c6f1c2`.

I independently pulled its **linux/amd64** manifest and exported its filesystem without executing it. `/var/lib/dpkg/status.d/libc6` confirms `Source: glibc`, `Version: 2.41-12+deb13u4`, `Architecture: amd64`. The ELF loader and libc are present; both `EUC-JISX0213.so` and `SHIFT_JISX0213.so` conversion modules are present. There is **no nscd file and no setuid/setgid file** in that base filesystem. I subsequently exported the original published amd64 application manifest `ghcr.io/threatflux/vertex_rust_sdk@sha256:13578551123923484a9ed91632f25ff81b1c272093c407da7baf0927bf5ca9d5` and independently confirmed the same libc version, present JIS modules, and absence of nscd and setuid/setgid files. The original arm64 final manifest `sha256:ab7e79b71273131f7ecb5c9099c94fc34c2920f6d9fcf1a17377dfcc395c6429` was then exported independently and confirmed the same libc revision, JIS modules, absent nscd, and absent setuid/setgid files. This final-image evidence is for the old scanned artifacts, not the replacement build. The application Dockerfile adds tini and the compiled CLI, and runs as `65532:65532`.

The workflow defaults to `linux/amd64,linux/arm64`, with PR builds restricted to amd64. `RUST_TEMPLATE_DOCKER_PLATFORMS` can override the published platforms. The base index also offers ppc64le, so its mere availability does not prove that an application ppc64le image was published. The alert export itself does not record an architecture. The immutable published application index `sha256:324c223852180cc4d704255060d4f0e12a5c1bfa30df4864107e1e7b62446e81` was independently inspected and contains only runnable amd64 and arm64 manifests, plus two attestations. Thus the Power8 exclusion is established for this actual published artifact. Recheck later published indexes before applying it to new artifacts. See [original image evidence](gcc-zlib-alert-review.md#artifact-and-observed-evidence).

**TP below means an accurate vulnerable-package/version match with the affected library code present**, not proven application exploitability. **FP means the affected architecture or component is absent**, even if a broad source-package version rule matches. An unavailable or unobserved application call path is recorded separately and is not used to relabel a correct vulnerable-package detection as FP. Reachability was assessed by reading `src/client.rs`, `src/auth.rs`, the manifest and local reqwest sources, plus searching `src/` for the affected C APIs. This is not a whole-program dependency or binary call-graph proof.

[Debian's glibc tracker](https://security-tracker.debian.org/tracker/source-package/glibc) still lists trixie `2.41-12+deb13u4` as vulnerable for these CVEs, with no DSA planned. The individual records below distinguish the fixed **unstable** package versions; those versions are not stable Debian 13 update recommendations.

## Shared remediation R

1. Track a **Debian 13 stable backport** containing each referenced upstream fix, or a supported stable runtime distribution that already contains them. Debian's current `no-dsa` disposition means a routine refresh to the latest Debian 13 base digest does **not** currently guarantee removal. Rust/crate upgrades also do not patch this system libc.
2. When fixed stable runtime packages become available, refresh the runtime digest and rebuild every published architecture; rebuild the builder as well so the copied tini and application remain compatible. Record actual package revisions and fixed-commit provenance in the review.
3. If a stable backport will not arrive within the project's risk window, evaluate a supported alternative runtime or a maintained patched Debian build. A musl migration needs an explicit compatibility trial for all features, native TLS, DNS and CLI behavior; it is not a drop-in claim. Avoid mixing Debian unstable libc into a stable image or copying an arbitrary standalone `libc.so`.
4. Until then, retain the open accurate detections and apply the per-alert controls. If accepting risk, record it explicitly with owner and review date. An architecture exclusion or absent-component statement should be scoped to the exact image/platform and revisited after image changes, without blanket CVE suppressions.

## Shared validation V and remaining evidence

Export the **complete rebuilt image** for every published manifest. Check package metadata and provenance against each Debian/CVE record; audit setuid/setgid bits, capabilities, loader paths, nscd presence and converter modules. Run CLI `--version`, `--help`, actual endpoint DNS resolution, and an HTTP request against a disposable local test service using production features. Exercise auth and both TLS feature combinations with existing tests. Run relevant upstream regression tests against the patched package in an isolated build fixture; destructive reproductions do not belong in production.

Rescan each architecture with a freshly updated Trivy database and archive JSON/SARIF plus immutable image digest. Compare all 14 alert IDs, distinguishing fixed packages, absent components and architecture exclusions. Do not claim these alerts fixed based solely on successful Rust tests or an empty Cargo audit. This review performed base and both old published-platform package/filesystem inspection, published-index inspection and source analysis; it did not execute exploit reproductions, inspect host sysctls, confirm repository-variable overrides, or inspect the completed release binary's dynamic imports.
