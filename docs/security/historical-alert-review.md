# Historical glibc code-scanning review

This records the original glibc-based artifacts. See the [subsequent remediation](remediation.md) for the static runtime fix and current alert dispositions.

Reviewed 2026-10-21. Scope: alerts **23–29**, Trivy OS-package findings for `libc6 2.41-12+deb13u4` at commit `3b990a75b9cef5fc43dffa45ad8851078177998f`. No alert was dismissed or suppressed during this review.

## Verdict and evidence boundary

All seven are **TP package matches**: Debian's own tracker lists this exact trixie glibc source version as affected, unfixed, with `unimportant` urgency. None is proven exploitable through this SDK. Reporting them as seven confirmed SDK vulnerabilities would overstate the evidence; reporting them as version-matching false positives would also be incorrect. The per-alert application assessments below distinguish these outcomes.

Evidence gathered from the existing published **amd64** image `ghcr.io/threatflux/vertex_rust_sdk@sha256:13578551123923484a9ed91632f25ff81b1c272093c407da7baf0927bf5ca9d5`:

- Image label `org.opencontainers.image.revision` equals the alert commit. Exported image package metadata confirms `libc6`, version `2.41-12+deb13u4`, architecture `amd64`.
- The runtime contains `/usr/local/bin/app` and `/usr/bin/tini`; `/usr/bin/ldd`, `/bin/ldd`, `/usr/bin/grep` and `/bin/sh` are absent. Its Dockerfile uses distroless Debian 13, UID/GID 65532, and a fixed exec-form `tini → app` entrypoint. A nonroot user does not prevent denial of service or memory corruption.
- Parsing the executable's ELF64 dynamic symbol table found 242 undefined symbols, including `pthread_create`, `dlopen` and `dlsym`, but **no `glob`, `glob64`, `regcomp` or `regexec` imports**. This supports the absent direct pattern-matching path; it is not a proof about every indirect call from libc or every loaded native library.
- Repository search across `src` found no libc glob/regex calls, unsafe blocks or explicit `ldd`/`dlopen` invocation. The process command in `src/auth.rs` invokes fixed `gcloud auth print-access-token` arguments; it does not execute an attacker-supplied ELF. Cargo includes Rust regex crates transitively; that alone does not invoke glibc's POSIX regex implementation.
- The workflow defaults to `linux/amd64,linux/arm64`, with PR builds on amd64. This review inspected the published amd64 filesystem/binary only. The alert payload contains no platform field; **arm64 artifact equivalence is unverified**. These CVEs are not established as amd64-only, so architecture alone does not dismiss them.
- Sourceware Bugzilla and the security-exceptions wiki returned access-denied responses. Vendor-dispute statements below are supported by the accessible Debian tracker, which links the original upstream reports; those original reports were not independently read. GNU manual documentation describes the regex API and dynamic-linker trust boundary, not proof of absence of these bugs.

Debian marks this unfixed/unimportant and refers to upstream's security exceptions. There is no discovered path from prompt/API/CLI input into libc `regcomp`/`regexec`; Rust regex dependencies do not establish one. | No fixed Debian version is available. Debian records that upstream does not treat this as a security issue. No prerequisite overflow was established; memory-safe Rust source alone does not prove native dependencies cannot contain one. | No fixed Debian version exists. Address any independently established memory-safety bug first; maintain current native dependencies and compiler hardening. If evaluating stronger isolation, separate untrusted native processing into a bounded worker. Validate any suspected prerequisite with a minimal reproducer and sanitizer-instrumented native code on both shipped architectures; require it to fail safely after its fix. A libc refresh alone is not a complete fix. |

For future ELF inspection, parse without execution in a sandbox; do not invoke `ldd` on untrusted binaries. If an application threat model requires stricter allocation isolation, assess worker process isolation. Maintain native dependency updates, eliminate any real address disclosures and memory corruption found in subsequent review, and avoid treating ASLR as the primary boundary. Validate with a concrete end-to-end leak/corruption chain if one is proposed, across both shipped architectures; reassess worker isolation if native untrusted-input processing is introduced. |

## Release follow-up

1. Rebuild from the refreshed pinned bases and lockfile, record the final image digest and libc package version, and scan **both** amd64 and arm64 with current Trivy databases and all severities. Do not rely on a `CRITICAL,HIGH`-only scan to show closure of these LOW findings.
2. Export each final runtime and inspect packages, entrypoint/user, absent diagnostic executables, dynamic imports and loaded native dependencies. The inspected old amd64 image supports this review but is not validation of the new build.
3. Preserve this record alongside any future VEX/exception decision, including exact digest, affected package, attack prerequisites, owner and reassessment date. Package inventory matches should remain distinguishable from application exploitability decisions. No global `.trivyignore` is justified by this review.
4. If removing glibc entirely is desired, evaluate a musl-linked minimal runtime as a separate compatibility change. Verify TLS, Google authentication, DNS/NSS behavior and both architectures. Removing a package changes applicability; switching distributions or libc is not proof that every analogous behavior disappears.
